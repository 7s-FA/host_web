# Robot3 공정 시뮬레이션

A제품 또는 B제품 1~2개의 주문 → 부품 적재 → 운반 → 티칭 조립 → 파렛트 적재 → 복귀를 웹에서 재생합니다. 기본 공정 지도는 시뮬레이션이며, **실물 상태 보기**에서는 ROS로 받은 위치와 장치 상태를 표시합니다. 별도의 **로봇 제어** 패널은 Host PC의 rosbridge와 준비된 M1·M2에 연결해 실제 이동을 요청합니다. 메인 화면과 Host 관제에서도 M1·M2의 **정지·정지 해제**를 요청하고 배터리를 확인할 수 있습니다. 전체 공정은 형제 `host_backend`와 연결한 `control.html`에서 제어합니다.

## 열기

- **웹 접속:** [Robot3 공정 시뮬레이션](https://7s-fa.github.io/host_web/) — GitHub Pages 배포 완료 후 이용할 수 있습니다.
- **설치 없이:** `robot3-simulation.html` 한 파일을 PC로 내려받아 브라우저에서 엽니다. 사진 9장과 한글 폰트도 포함되어 있어 인터넷 없이 동작합니다.
- **로컬 서버:** `bash start.sh` 실행 후 `http://localhost:8082`에 접속합니다.
- **VS Code Remote SSH:** Ports 탭에 `8082`를 추가하고 전달된 localhost 주소를 엽니다. 서버는 기본적으로 127.0.0.1에만 바인딩됩니다.

## Host PC 한 번에 실행

`final_project/host_web`과 `final_project/host_backend`를 함께 둔 관제 PC에서는 최상위 공통 실행기를 사용합니다. 현재 PC에서 웹(8082)·rosbridge(9090)·rosapi·기존 관제 백엔드를 한 번에 실행하려면:

```bash
bash $HOME/final_project/start_host.sh
# 노드를 실행하지 않는 점검
bash $HOME/final_project/start_host.sh --check
```

공통 설정은 `../config/host.env`, 빌드·로그는 `../.runtime/host/`입니다. 현재 폴더의 `bash start_host.sh`는 기존 의미대로 **웹·rosbridge·rosapi만** 실행합니다. 상세 사용법과 모의 검증 절차은 [관제 PC 안내](../README.md)를 확인하세요.

아래는 공통 실행기 없이 `host_web`을 단독 clone한 경우의 준비 방법입니다. 형제 폴더 `../host_backend`를 기본 사용하며 다른 위치는 `HOST_BACKEND_DIR`로 지정합니다. **이 방법은 Git으로 clone한 전체 소스 기준입니다.** 사이트의 `host-test.zip`은 HTTP 시험용이며 통합 실행 스크립트를 포함하지 않습니다.

최초 준비는 한 번만 실행합니다. 내려받은 기존 빌드 경로와 섞이지 않도록 `install_local`에 Action 타입을 빌드합니다.

```bash
sudo apt update
sudo apt install ros-jazzy-rosbridge-suite python3-colcon-common-extensions
source /opt/ros/jazzy/setup.bash
cd ../host_backend
colcon --log-base log_local build \
  --base-paths src/host_pkg \
  --build-base build_local \
  --install-base install_local \
  --packages-select host_pkg
```

이후에는 터미널 하나에서 실행합니다.

```bash
cd ../host_web
bash start_host.sh
```

Host PC 브라우저에서 `http://localhost:8082/?live=1`을 엽니다. 실행 스크립트는 ROS 환경과 Action 타입을 불러오고 기본 `ROS_DOMAIN_ID=40`, `ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET`, `RMW_IMPLEMENTATION=rmw_fastrtps_cpp`로 `host/host_control.launch.py`를 실행합니다. 두 서버는 같은 PC에서만 접속하도록 바인딩합니다. 로봇과 Host의 네트워크·DDS 검색 설정도 서로 맞아야 합니다.

각 이동 로봇은 Pi에서 `host-ready` 준비를 마쳐 `process` 모드와 Action 서버가 실행 중이어야 합니다. 이 런치는 개별 제어·실제 상태 확인용이며, 전체 공정 제어기 `host_backend/src/host_pkg/src/main.py`와 로봇 준비 명령은 실행하지 않습니다. 시작할 때 이동 명령도 보내지 않습니다.

`Ctrl+C`로 웹 서버·rosbridge·rosapi를 함께 종료합니다. **웹 통신 종료는 로봇 정지 명령이 아니므로, 이동 중인 로봇은 먼저 패널의 정지 버튼으로 정지 결과를 확인하세요.** 필수 프로세스 하나가 종료되면 나머지도 정리합니다. 8082 또는 9090 포트가 이미 사용 중이면 기존 서버를 종료하라는 오류를 표시합니다.

## 실물 상태 보기

Host PC에서 `bash start_host.sh`로 실행한 뒤 메인 화면의 **실물 상태 보기**를 누르거나 `http://localhost:8082/?live=1`을 엽니다. 기본 주소는 기존 데모를 유지합니다.

- M1·M2는 `/burger1/amcl_pose`, `/burger2/amcl_pose`의 `map` 좌표와 quaternion 방향을 기존 지도에 표시합니다. 첫 좌표 수신 전에는 아이콘을 숨기고, 좌표가 3초 이상 오래되면 흐리게 표시하며 화면의 아이콘 움직임을 멈춥니다. **Host와 로봇의 시각을 동기화해야 합니다.**
- `live-map-config.js`에는 M1·M2별 최신 AMR WP1~4 기준의 구간별 보정이 있습니다. 기존 SVG는 정밀 축척 지도가 아니므로 현장 위치와 대조해 보정해야 합니다.
- 로봇팔 1~3은 Action의 실행·일시정지·완료 상태를 표시하며, 실행 중일 때 동작 애니메이션을 보여줍니다. 실제 관절 자세를 재현하는 기능은 아닙니다. ROSAPI로 발행 노드를 확인하지 못하면 상태 미확인으로 표시하고 애니메이션을 멈춥니다.

작업 시작 전에 실물 상태 화면을 열어 두세요. 로봇팔 피드백은 상태가 바뀔 때 전달되므로, 작업 도중 새로 열거나 연결이 복구되면 해당 작업의 새 피드백을 받을 때까지 **상태 미확인**으로 표시합니다.

상태 모니터링은 수신 전용이며 웹 주문·재생 상태를 송신하지 않습니다. 사용자가 M1·M2의 **정지·정지 해제**를 누르면 해당 실물 로봇에 Action을 보냅니다. 전체 주문·단계 진행은 통합 실행 후 `control.html`에서 제어하고, 개별 이동은 로봇 제어 패널을 사용합니다.

## 장치 연결 표시등

공정 시뮬레이션·실물 상태 보기·Host 관제에서 **Host·M1·M2·자재창고·제작공정**의 연결 표시등을 확인할 수 있습니다. Host PC의 HTTP `localhost`·`127.0.0.1` 화면에서 동작하며, 공개 사이트와 오프라인 HTML에서는 회색 **Host PC에서 확인** 안내를 표시합니다.

- 초록 **연결됨**: Host는 최근 `/ros_to_web` 상태 수신, 장치는 해당 Action 상태 발행자 확인 기준입니다.
- 노랑 **일부 연결 / 확인 불가**: 제작공정의 팔 2·3 중 하나만 연결됐거나 장치 검색 응답을 확인할 수 없습니다.
- 빨강 **연결 끊김**: 장치 제어 서버가 감지되지 않거나 Host 상태 수신·ROS 연결이 끊겼습니다. 회색 **확인 중**은 최초 확인 대기입니다.

장치 검색은 1초 간격이며, 확인 응답과 Host 상태는 3초까지만 유효합니다. 자재창고는 로봇팔 1, 제작공정은 로봇팔 2·3을 함께 확인합니다. 리니어·카메라 개별 정상이나 공정 완료를 뜻하지 않습니다. 웹 서버와 rosbridge만 실행하면 Host 통신 표시등은 켜지지 않으며, `/ros_to_web`를 발행하는 기존 Host 프로그램도 실행되어야 합니다. 표시등은 수신·조회만 하고 동작 명령을 보내지 않습니다. 관제의 주문·작업 로그용 Host 어댑터 연결과는 별도입니다.

## M1·M2 실물 정지·해제와 배터리

메인 공정 시뮬레이션(`/`), 실물 상태 보기(`?live=1`), Host 관제(`control.html`)에서 **M1 정지·M2 정지**를 사용할 수 있습니다. HTTP의 `localhost` 또는 `127.0.0.1` 화면에서 rosbridge가 연결되어야 하며, 공개 사이트에서는 비활성화됩니다. HTTP Host 어댑터가 없거나 응답하지 않아도, 로봇이 동작 중이거나 위치·상태 수신이 오래되어도 rosbridge 연결이 있으면 정지를 요청할 수 있습니다.

선택한 로봇에만 `EMER_STOP`을 보내며 Host 전체 주문이나 다른 로봇·팔을 일시정지하지 않습니다. 로봇별 요청 대기와 결과를 따로 표시합니다. 최종 성공 응답을 받아야 **정지 확인**으로 표시하며, 10초 안에 결과가 없거나 오류·연결 끊김이 발생하면 **정지 여부 미확인**입니다. 재연결해도 이전 정지를 자동 재전송하지 않고 `RESTART`도 자동으로 보내지 않습니다. 통신 연결이나 버튼 클릭만으로 정지를 확인한 것으로 판단하지 마세요. 구현은 `robot-stop-client.js`와 `robot-stop.js`, Action 계약은 [Host 관제 연결 안내](HOST_CONTROL_GUIDE.md#m1m2-실물-정지-action)에 있습니다.

**M1 정지 해제·M2 정지 해제**는 사용자가 누를 때만 `RESTART`를 보냅니다. 해당 로봇의 `motion_owner/communication_status`를 최근 3.5초 이내에 받고, 실행 중 임무와 대기 요청이 없어야 활성화됩니다. AMR이 최신 odom의 정지 상태도 확인하며, 최종 성공 응답 전에는 해제 확인으로 표시하지 않습니다. 해제는 이전 이동을 재개하지 않지만 **실행 중인 Host 자동 공정이 새 이동 명령을 보낼 수 있으므로 Host 상태를 먼저 확인하세요.**

메인 데모·실물 보기·Host 관제·로봇 제어 패널에 **M1·M2 배터리 전압과 추정 잔량**을 표시합니다. `/burger1/battery_state`·`/burger2/battery_state`의 실제 전압을 사용하고, 10.5~12.3V를 0~100%로 환산합니다. 전압 기반 추정치이며 정확한 충전량이 아닙니다. 5초 이상 새 값이 없거나 연결이 끊기면 마지막 값을 오래된 값으로 표시하고, 미수신·비정상 값은 미확인으로 표시합니다. 공개 사이트에서는 로컬 연결 안내를 표시합니다. 단위와 계산 근거는 [배터리 수신 계약](HOST_CONTROL_GUIDE.md#m1m2-배터리-수신)에 있습니다.

## 최신 버전 적용

실행 중인 서버를 `Ctrl+C`로 종료한 뒤 Host PC에서 실행합니다.

```bash
cd ~/host_web
git pull --ff-only origin main
bash start_host.sh
```

브라우저에서 `Ctrl+Shift+R`로 새로고침합니다. 이동 중인 로봇은 서버 종료 전에 패널에서 정지 결과를 확인하세요. HTTP 시험 ZIP은 최신 파일을 새 폴더에 풀고 `python3 web/host/server.py`로 실행합니다.

## 기본 데모 화면 구성

- 왼쪽: 큰 공정 시뮬레이션 지도, 재생 제어, 장비 상태, 현재 공정 사진·이벤트.
- 오른쪽: 실제 조작 가능한 Host PC GUI. A제품/B제품·1개/2개 버튼 선택, 주문 시작, 주문 수량·운송 잔여·완제품 잔여·적재 완료 카운트를 함께 표시합니다.
- 모바일: Host GUI를 위에, 시뮬레이션을 아래에 배치합니다.

## 기본 데모 조작

1. Host 관제와 같은 방식으로 **A제품/B제품**, 수량 **1개/2개** 버튼을 선택합니다. 선택한 제품과 수량은 버튼 아래에 표시됩니다.
2. `주문 · 시작`을 누르면 운송 잔여와 완제품 잔여를 주문 수량으로 초기화합니다.
3. 일시정지, 이전/다음 이벤트, 진행 막대로 시뮬레이션을 확인합니다.
4. 지도 구역을 누르면 그 장소의 사진을 표시합니다. `자동`으로 현재 공정 사진을 따라갈 수 있습니다.
5. 사진을 누르면 확대합니다. 현장 사진 탭에는 전체 사진이 있습니다.
6. `기록 내려받기`는 현재 시점까지의 이벤트·카운트를 JSON으로 저장합니다.
7. 새 주문 제품·수량을 바꾸려면 `초기화`를 누릅니다. 완료 후에는 바로 새 주문을 넣을 수 있습니다.

A·B제품은 같은 설명용 이동 경로와 공정 시간을 사용합니다. 선택한 제품은 주문 표시·지그 표기·이벤트·내려받는 기록에 반영되며, B제품의 실제 동작이나 공정 시간을 재현하는 것은 아닙니다. 통합 실행에서는 `host_backend`가 실제 Action 완료 결과로 주문을 진행합니다.

## 공정 규칙

- 제품 1개당 부품 3개. M1부터 시작해 M2와 번갈아 운반합니다.
- 운송 잔여: 적재가 끝난 이동 로봇의 제작공정 이동 시작 시 한 번 감소합니다.
- 완제품 잔여: 로봇팔 3의 파렛트 적재 성공 시 한 번 감소합니다.
- 주문이 2개 이상이면 M1이 자재창고에 도착하는 순간 M2가 초기위치에서 대기장소로 출발합니다. 1개 주문에서는 M2가 초기위치에 머뭅니다.
- 첫 조립이 시작되면 다음 이동 로봇이 자재창고에서 부품을 준비합니다.
- 제작공정에는 중앙 교차 통로에서 오른쪽으로 직선 이동해 도킹합니다. 도킹 직전 추가 꺾임은 없습니다.
- 출발 방향이 다르거나 코너에 도착하면 이동을 멈추고 차체를 제자리 회전시킨 뒤 직선 주행합니다. 회전은 90도당 1초의 설명용 시간으로 부드럽게 표시하며 공정 일정에도 포함합니다. 전진 구간에서는 이동 로봇 전방이 진행 방향을 향하고, 후진 구간에서는 바라보는 방향을 유지하며 뒤로 이동합니다. 대기장소에는 아래쪽을 바라보며 전진 주차합니다. 출차는 10cm 후진·정지 → 180도 회전 → 전진 주행합니다.
- 초기위치에서 두 이동 로봇은 왼쪽 벽의 ArUco 마커를 바라봅니다. 전방 카메라로 마커에 정렬하고 후방 IR 센서가 검은 감지선을 감지하면 멈추는 기준입니다.
- 초기위치 → 창고: 왼쪽을 바라본 채 중앙 통로까지 후진 → 우회전 90도 → 위쪽 창고로 전진.
- 창고 → 공정: 위쪽을 바라본 채 교차 통로까지 후진 → 우회전 90도 → 오른쪽 공정으로 전진 도킹.
- 공정 → 초기위치: 제작공정에서 로컬 10cm 후진·정지 → 제자리 180° 회전 후 전진으로 복귀합니다. M1은 WP3 → WP1, M2는 WP3 → WP4를 지나 각 초기위치로 복귀합니다. WP4는 M2의 출차·복귀 합류점입니다. 경유점에서는 Host의 별도 승인을 기다리지 않습니다.
- 대기장소 → 초기위치: 10cm 후진·정지 후 180도 회전하고, 중앙 통로를 전진해 해당 주차칸 높이에서 좌회전한 뒤 진입합니다. 두 이동 로봇 모두 왼쪽 벽을 바라보며 복귀 완료합니다.
- 대기장소에는 ArUco 마커가 없으며 전진 주차 중 후방 IR 센서가 검은 감지선을 감지하면 정지합니다. 다른 목표 위치에는 ArUco 표식과 후방 적외선 센서용 검은 감지선을 표시합니다. 현재 표식은 개념 표시이며 실제 마커 ID·사전·센서 신호 판정은 실물 설정 시 확정합니다.
- 다음 제작공정 운송은 앞 제품의 파렛트 적재, 앞 이동 로봇의 대기장소 도착, 다음 부품 3개 적재를 모두 확인한 뒤 시작합니다.
- 리니어 모터는 매 제품마다 조립 지그 준비 → 조립 → 초기위치 복귀를 수행합니다.
- 운송 잔여가 0이어도 마지막 운송 이동 로봇이 제작공정에 도착·도킹할 때까지 다른 이동 로봇은 대기장소에 머뭅니다. 도킹 완료 후 대기 이동 로봇이 초기위치로 복귀합니다. 2개 주문에서는 M2 도킹 완료 → M1 복귀 순서입니다. 마지막 이동 로봇은 자신의 조립 작업 완료 후 초기위치로 복귀합니다.
- 마지막 완제품 적재와 두 이동 로봇 복귀가 모두 끝나야 주문 완료입니다.

사진은 제공된 Drive 폴더에서 가져왔으며 출처는 `assets/sources.json`에 있습니다. 사진은 웹용으로 축소했습니다. 지도는 제공된 사진 기준의 세로형 배치입니다. 사용자가 지정한 방향인 왼쪽 아래 초기위치(M1 위·M2 아래), 중앙 위 자재창고, 오른쪽 아래 제작공정을 중앙 통로로 연결합니다. 교대 대기장소는 전체 맵 사진에서 중앙 아래쪽 테이프 박스로 표시된 곳입니다. 제작공정은 같은 작업대 위에 조립 로봇팔 2, 가로 리니어 지그, 적재 로봇팔 3과 파렛트를 배치했습니다. 사진에서 파악한 상대 배치이며 실측 좌표나 충돌 회피 경로는 아닙니다. 각 동작의 시간은 설명용 고정값으로 실측값이 아닙니다. 실패·재시도는 이 버전에 포함하지 않았습니다.

## 호스트 PC 통신 시험

공개 웹사이트의 [다운로드·사용법](downloads.html)에서 **HTTP 시험 패키지**를 받아 압축을 푼 뒤, `robot3_host/`에서 `python3 web/host/server.py`를 실행하고 `http://127.0.0.1:8082/?host=1`에 접속합니다. Python 3.10 이상만 필요합니다. Git으로 받은 저장소에서는 `python3 host/server.py`를 사용합니다.

호스트가 중간 노드에서 끊지 않고 다음 작업 완료 지점까지의 실행을 지시하고 웹이 완료를 회신합니다. **다음 단계**, **완료 회신 후 자동 진행**, **일시정지·재개**, **시험 초기화**, **통신 기록**을 제공합니다. 완료 신호 중복·순서 오류·이전 주문 신호를 검사하며 통신 실패 시 정지합니다. 실제 장비는 연결하지 않습니다. 기존 자동 시뮬레이션은 공개 사이트에서 그대로 사용할 수 있습니다.

실행 방법과 프로토콜: [host/README.md](host/README.md).

## 단계별 실행과 전환 조건 (2026-09-28)

- 주문 시작 옆 **단계별 실행**을 누르면 첫 단계를 실행하고 목적지·작업 완료 경계에서 기다립니다. **다음 단계 실행**으로 이어갑니다. 회전 코너·주행 중간에는 추가 대기하지 않습니다.
- 시뮬레이션 왼쪽의 전환 조건: 빨간 동그라미는 미완료, 초록 동그라미는 완료입니다. 도착, 적재 3개, 조립, 리니어 준비·원점, 파렛트 완료와 해당 운송의 선행 조건을 표시합니다.
- Host 연결 상태에서 단계별 실행을 누르면 자동 진행을 해제하고 `start` 또는 `next`를 보냅니다. 작업 완료 후 `order_id / seq / time`을 포함한 ACK를 보내며, Host 응답의 `acked_seq`가 확인돼야 ACK 항목이 초록색이 됩니다.
- 작업 조건은 웹 시뮬레이션의 모의 완료 이벤트입니다. 실제 로봇의 Nav2·ArUco·후방 IR 센서 신호는 아직 연결되지 않았습니다. 연결이 끊기면 다음 단계 버튼이 비활성화됩니다.
- 기존 주문 시작과 Host 자동 진행 체크박스는 그대로 사용할 수 있습니다. 로컬 시험은 최신 소스를 `git pull`한 뒤 서버를 재시작하고 브라우저를 새로고침하세요.

## Host 실장치 관제 화면

[웨이포인트 화면](waypoints.html)은 공개된 M1의 `map` 좌표 JSON과 Confluence 도면, 목적지별 경유 순서를 표시합니다. 1~4번은 최종 목적지가 아니라 경유·회전 지점입니다. [시뮬레이션 지도](index.html)는 같은 번호를 세로 배치도의 개념 위치에 표시하고 두 이동 로봇이 해당 지점을 통과하도록 경로를 나눕니다. WP1은 M1 초기위치, WP4는 M2 초기위치의 통로 합류점이며 WP3는 제작공정 합류점입니다. 경유점에서 Host 완료 단계를 추가하지 않습니다. 목적지별 순서는 [routes-burger1.json](routes-burger1.json)과 [routes-burger2.json](routes-burger2.json)에 있으며 실제 지도에서 확인해야 합니다. 실측 좌표를 시뮬레이션 픽셀에 그대로 환산한 것은 아니며 실제 Nav2·도킹 제어는 아직 연결되지 않았습니다.

[Host 관제](control.html)는 지도·시뮬레이션 엔진 없이 **A제품/B제품**과 수량 **1개/2개**를 버튼으로 선택해 주문합니다. 통신 상태는 **M1·M2·자재창고·제작공정** 네 단위로 표시하며, 제작공정은 로봇팔 2·3, 리니어와 카메라를 통합합니다. 각 장치와 Host의 **로그** 버튼은 작은 팝업으로 기록을 표시하고, 통신이 끊겨도 마지막 로그를 확인할 수 있습니다. 공개 Pages에서는 미연결 안내만 보이며, Host PC에서 `python3 host/server.py`를 실행한 뒤 `http://127.0.0.1:8082/control.html`로 접속합니다. 실제 ROS 2 장치와 통신하려면 팀의 Host 어댑터가 ROS Action 결과를 검증한 후 [관제 API 계약](HOST_CONTROL_GUIDE.md)대로 상태를 보고하고 명령을 수락해야 합니다. 통합 폴더에는 `host_backend`의 실행부가 연결되어 있습니다. `--mock`로 실제 ROS Action 경로를 모의 검증할 수 있습니다. 웹만 내려받은 ZIP에는 이 실행부가 포함되지 않습니다. 다음 단계 버튼은 어댑터가 모든 선행 조건 완료를 보고할 때만 활성화됩니다. 메인 공정 시뮬레이션에서도 같은 A제품/B제품·1개/2개 선택 버튼을 사용하며, 지도는 두 제품에 공통 설명용 동작을 표시합니다.

## Host 시스템 설정

주문 수량 범위·기본값, ROS 2 장치 주소, 작업 명령, 완료 판정, 다음 명령 조건은 **system-config.json**에서 관리합니다. [SYSTEM_CONFIG_GUIDE.md](SYSTEM_CONFIG_GUIDE.md)에 수정 위치와 적용 여부를 정리했습니다. `python3 host/system_config.py --write-web-policy`로 검증·웹 수량 정책을 생성한 뒤 Host를 재시작하세요. 이 파일의 자동 공정용 통신·완료 규칙은 연결 예정 설정입니다. 로봇 제어 패널의 개별 이동과 구분합니다.

### 이동 로봇 내부 주행 단계

시뮬레이션 왼쪽의 **이동 로봇 주행 단계**에서 M1·M2를 선택해 확인합니다. 빨간 원은 미완료, 초록 원은 완료이며 실행 중인 단계에는 별도 표시가 붙습니다. 표시되는 카메라·거리·IR 신호는 모두 웹 모의 신호입니다.

초기위치 → 자재창고의 기본 순서는 다음과 같습니다.

| 단계 | 이동 로봇 내부 동작 | 다음 단계로 넘어가는 조건 |
| --- | --- | --- |
| 1 | 로컬 cmd_vel로 10cm 후진 | 후진 거리 10cm 도달 |
| 2 | 제자리 180° 회전 | 회전 완료 |
| 3 | Nav2로 M1은 WP1, M2는 WP4까지 전진 | 해당 웨이포인트 도착 |
| 4 | Nav2로 WP2까지 이동 | WP2 도착 |
| 5 | 전방 카메라로 ArUco 마커를 추종하며 정렬·전진 | 후방 IR 감지선까지 접근 |
| 6 | 후방 IR 감지 → 정지 | 정지 후 Host에 도착 완료 회신 |

M2는 기존 공정 스케줄을 유지합니다. M1의 자재창고 도착 시 초기위치에서 출차해 WP4를 거쳐 대기장소로 갑니다. 앞 이동 로봇의 제작공정 진입 후 대기장소에서 10cm 후진·180° 회전 → WP2 → ArUco 정렬·전진 → 후방 IR 정지 순으로 자재창고에 진입합니다. 대기장소에는 ArUco 마커가 없으며 전진 진입 후 IR로 정지합니다.

이 단계는 이동 로봇 내부 상태와 진행 피드백입니다. Host는 목적지 이동을 지시하고, 이동 로봇이 Nav2·카메라·IR 동작을 처리합니다. 중간 웨이포인트마다 Host 승인을 기다리지 않으며 최종 IR 정지 뒤 도착 완료로 처리합니다. 시뮬레이션 이벤트의 `navigation_start` / `navigation_done`은 단계 코드와 제어 방식 확인용이며 실제 ROS2 메시지를 송수신하는 구현은 아닙니다. 코드: `engine.js`의 `navigationFor()` / `navigationState()`.
